# 群关联监控惩罚插件 (astrbot_plugin_group_monitor)

> 适用于 [AstrBot](https://github.com/AstrBotDevs/AstrBot) 的群管联动插件。监控新成员加群，若在指定缓冲时间内未加入目标关联群，则自动在当前群执行**禁言**或**踢出**；成员加入目标群后自动解除监控群禁言。

## 功能特性

- **主从群联动**：进群后未加目标群 → 自动禁言/踢出；加入目标群 → 自动解禁。
- **时间单位友好**：缓冲时间、禁言时长支持 `天 / 小时 / 分钟 / 秒`（如 `3天`、`1.5天`、`2小时`、`30分钟`、`60秒`），纯数字按秒。
- **规则别名 & 动态标题**：每条规则可命名，WebUI 中实时显示。
- **入群自动 @ 提醒**：进群即 @ 该成员并发送验证提示。
- **踢出 / 禁言 双模式**：可配置直接踢出，或禁言一段时间。
- **诊断指令**：内置 `群监控自检` / `群监控测试` / `群监控调试`，快速排查适配器与权限问题。

## 兼容性说明（重要）

本插件通过标准 **OneBot v11** 动作（`set_group_ban`、`set_group_kick`、`send_group_msg`）操作群管，因此兼容所有以 OneBot v11 接入 AstrBot 的协议端，包括但不限于 **NapCat**、**SnowLuma** 等。

> ⚠️ **SnowLuma 已知问题已修复（v1.5.1）**：
> SnowLuma 的 `get_group_member_info` 接口会报错（`group member robot classification unavailable`），导致旧版插件无法判断「对方是否已加入目标群」，从而**对已合规成员过度惩罚**（已加目标群的人也被禁言，再进目标群又解禁）。
> 本版已改为**基于入群/退群事件自行维护目标群成员名单**，彻底规避该接口，SnowLuma 下行为恢复正常。

## 使用前提

- 机器人在**监控群（群1）必须是管理员或群主**，否则无法禁言/踢出。
- 机器人在**目标群（群2）建议也设为管理员/群主**：部分环境下机器人非管理员时，目标群的新成员入群通知可能不上报，导致「加入目标群自动解禁」无法触发。

## 安装

1. AstrBot 面板 → 插件市场搜索 `astrbot_plugin_group_monitor` 安装；或
2. 将本仓库克隆/下载到 AstrBot 的 `data/plugins/astrbot_plugin_group_monitor/` 目录，重启 AstrBot。

## 配置

通过 WebUI 的插件配置添加规则（`_conf_schema.json` 提供表单）：

| 字段 | 说明 |
| --- | --- |
| name | 规则名称/备注（留空自动用监控群号） |
| group1 | 监控群号（进群的群） |
| group2 | 目标群号（必须加入的群） |
| punish | 惩罚动作：`mute`(禁言) / `kick`(踢出) |
| delay | 缓冲时间(秒)，进群后等待多久检测，默认 60 |
| mute_duration | 禁言时长(秒)，默认 86400(1天) |

## 指令说明

> 以下指令仅限 **群主 / 群管理员 / Bot 管理员** 使用。

- `群监控帮助` / `群互联帮助`：查看指令帮助。
- `添加群监控 <监控群> <目标群> [禁言/踢出] [缓冲时间] [禁言时长] [规则名称]`
  - 例：`添加群监控 111 222`（默认禁言，缓冲60秒，禁言1天）
  - 例：`添加群监控 111 222 踢出 10分钟 0 粉丝二群联动`
  - 例：`添加群监控 111 222 禁言 1天 30天 临时监控`
- `群监控列表`：查看所有规则。
- `删除群监控 <序号>`：删除规则。
- `设置惩罚 <序号> <禁言/踢出> [禁言时长或缓冲时间] [缓冲时间]`：调整规则。
- **诊断指令**：
  - `群监控自检`：检查适配器类型 + 机器人在各监控群的身份（SnowLuma 下 `get_group_member_info` 受限，会提示用测试指令定论）。
  - `群监控测试 <群号> <测试QQ> [秒数]`：对指定人做一次「禁言→自动解除」，验证 OneBot 动作链路是否通畅。
  - `群监控调试 开|关`：开关原始事件日志，用于确认适配器是否正确转发 `group_increase` 入群事件。
  - `群监控重建缓存`：重建目标群成员名单缓存（见下方 FAQ「冷启动」说明）。

## 工作原理

1. 监听 `group_increase` 入群事件。
2. 若加入的是**监控群(群1)**：发送验证提示，并等待 `delay` 后检查该成员是否在**目标群(群2)**（基于本插件维护的成员名单）。不在 → 执行惩罚。
3. 若加入的是**目标群(群2)**：自动解除其在监控群的禁言。

## 常见问题（FAQ）

**Q：换了 SnowLuma 后禁言/踢人失效，还显示「解除禁言」？**
A：先确认 SnowLuma 登录号在监控群是**管理员/群主**（权限按账号走，换协议端易用错号）。若权限正常，用 `群监控测试 <群号> <小号QQ>` 验证：若指令回显成功但小号在 QQ 里没真被禁，说明 SnowLuma 的 `set_group_ban` 未真正执行（动作层问题，需看 SnowLuma 侧）；若真被禁，则问题已在本版修复的过度惩罚逻辑中解决。

**Q：为什么「已加目标群的人也被禁言了」？**
A：旧版依赖 SnowLuma 损坏的 `get_group_member_info`，现已改为事件维护成员名单，该问题已修复。

**Q：冷启动盲区——对方「早于插件启动前就已在目标群」，后来才进监控群，会被误罚吗？**
A：会。本插件用「入群/退群事件」自维护目标群成员名单，但事件只在插件启动**后**才会被记录。若有人在插件启动前就已待在目标群、之后才进监控群，缓存里没有他 → 会被误判为「未加目标群」而错误禁言，且因无新的「进目标群」事件，也不会自动解禁。

解决方法（二选一）：
1. 插件（或 AstrBot）启动/push 后，在群里发 `群监控重建缓存`，立即用 `get_group_member_list` 刷新各目标群成员名单；之后该场景即正确。
2. 让该成员「退群再重加」目标群，触发一次入群事件写入缓存。

> 注：`get_group_member_list` 在 SnowLuma 下若也被限制（与 `get_group_member_info` 同理），重建缓存数字可能为 0，此时仍建议改用 NapCat，或让成员退群重加。NapCat 等标准端无此问题。
